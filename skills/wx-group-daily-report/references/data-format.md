# 数据格式与解析规则（源自 F:\dev\wx-group-collector\DATA_GUIDE.md）

读取顺序有变时以仓库里的 DATA_GUIDE.md 为权威，本文件是整理时必须知道的要点。

## 增量读取（核心：不按自然天分割）

- 检查点文件 `state.json` 与 SKILL.md 同目录：`{"last_run": "<iso>", "files": {"messages-2026-11-21.jsonl": 217, ...}}`，数值 = 该文件已分析的行数。
- **目标群以 `F:\dev\wx-group-collector\config.json` 的 `groups` 数组为准**（每次运行现读，用户会改监听对象，勿缓存勿硬编码）。行级过滤：`group` 字段不在名单里的行直接跳过；换群后文件里残留的旧群消息不产生输出，检查点按行数照常推进（行被"消费"）。
- 每次运行：`ls data/messages-*.jsonl` 按文件名日期升序，逐文件 `tail -n +<已处理行数+1>` 取新行，拼接成增量集。新出现的日期文件从第 1 行读。
- **行序即时间序**：文件按写入顺序追加，跨文件按文件名日期排序拼接；个别"补报"行时间戳偏旧属正常，按行序处理。
- 采集器会在零点后仍向新日期文件写入前一晚持续同步的消息——这正是必须跨文件拼接的原因。
- voice-transcripts / files-index 不做增量，仍按需查询（体量小）。**files-index 跨天匹配**：增量消息里的"文件"消息要同时查消息所在日期与相邻日期（±1 天）的 `files-index-*.jsonl`——文件本体常在消息之后才下载完成，索引可能落在次日的文件里。语音转写用消息行自身的 `iso` 作 `orig_iso` 匹配。
- 已知限制（DATA_GUIDE 记载，可忽略）：30 分钟内完全相同的文本可能被采集端去重；采集器重启间隙可能缺消息。
- 更新 state.json 的时机：飞书推送成功后；失败则不推进（下次重跑同一窗口）。

## 按天产出的文件

| 路径（相对仓库根） | 内容 | 用法 |
|---|---|---|
| `data/messages-YYYY-MM-DD.jsonl` | 主消息流 | 必读，UTF-8 每行一个 JSON |
| `data/voice-transcripts-YYYY-MM-DD.jsonl` | 语音转写兜底 | 主消息流出现 `[语音] N"` 占位时按 `orig_iso` 查 |
| `data/files-index-YYYY-MM-DD.jsonl` | 群文件索引 | 消息里出现"文件 X"时按文件名+就近时间查，`copied_to` 是本体路径 |
| `data/files/YYYY-MM/` | 文件本体 | 需要内容时读 |

## 消息字段

`ts`/`iso` 是**检测时间**而非发送时间；刷屏批次会挤在同一秒，真实先后以**行序**为准。`group` 群名；`content` 消息文本；`is_at_me` 是否@本机账号（日报口径说明里提一句当日是否有）。`source`：`live`=实时采集，`history`=历史导入（自带 `image` 相对路径指加密 .dat），`backfill`=漏记补填（ts/iso 为按 .dat 落盘时间推算的近似值，图片类自带 `image_path` 绝对路径指可读 PNG）。

## content 七种形态

| 形态 | 识别 | 处理 |
|---|---|---|
| 纯文本 | 原样 | 直接总结 |
| 语音带转写 | 前缀 `语音N"秒` | 剥前缀，后面就是转写文字 |
| 语音占位 | `[语音] N"` | 用该行 `iso` 作 `orig_iso` 查 voice-transcripts；查不到就没有 |
| 文件 | `文件\n名称\n…`（变体：未下载/下载中） | **必须溯源**：查 ±1 天的 files-index → 有 `copied_to` 且是业务文件（pdf/docx/xlsx/csv/txt）→ 读本体、内容并入报告（纪要/BP/融资材料是项目信息的重要来源）；是采集器测试文件（poc/*.py/tar.gz 等）→ 过滤。索引里也没有 / "对方上传中/未下载" → 报告附注注明"需重传" |
| 图片/视频/表情 | 图片的 content 为 **`图片`**（无方括号！2026-11-23 起才有记录，更早的图片消息无任何痕迹）；视频/动画表情仍为 `[视频]` `[666]` 等占位 | 图片按 `msg_iso` 查 files-index：消息记录自带 `image_path` 时直接读该 PNG;否则**按 msg_iso 查 files-index 优先找带 `decoded_to` 的条目**（`source:"clipboard"`，指向 `data\images\decoded\<yyyy-mm>\*.png`，可直接视觉读图，条目附 sha256/width/height）；没有 decoded 条目再看 `kind=="image"` 的加密 .dat 原件（微信 4.x 新加密，暂不可视）。报告口径：有 decoded PNG 时读图并摘要内容；仅有 .dat 时附注"含 N 张图片（原件已归档，暂不可预览）"。孤立图片/表情忽略。补录记录分两代：11-23 历史导入（`source:"history"`）用 `image` 字段指加密 .dat（相对 data 目录的路径）；2026-11-24 起的补录记录（`source:"backfill"`）用 `image_path` 指向可读 PNG |
| 合并转发 | `聊天记录…昵称: 内容` | **全数据里唯一带发送者的地方**，保留昵称信息 |
| @消息 | `@某某 内容` | @ 文本在 content 内，是"相关人"的合法来源 |

## 语义红线

1. **没有发送者字段**——除合并转发 `昵称:` 前缀外，一律不写"某某说"。宁可无主语。
2. 30 分钟内文本完全相同的消息可能被去重只记一条；采集器重启间隙可能缺失——小概率，忽略。
3. 消息按天分文件，`iso` 均为 +08:00。

## 实战经验（2026-11-21 首跑）

- 工具面:运行会话通常有 `WebSearch`/`WebFetch`——新闻链接读原文、群内关键事实(融资/估值/人事)核验、机构公开背景扩充均可使用;约定:web 补充信息标 🔍 并注明来源与检索日期,与群内口径冲突时两边并列,涉密内容不检索,班次合计 ≤10 次。
- 一天 217 条里有效投资内容约 60 条，其余是测试/闲聊——过滤要果断。
- 检测时间可能集中在一个补报批次（如全部挤在 16:12–16:16），但内容时序跨越全天（"晚上约了语音"和"聊完了"同批出现）：以内容逻辑定先后，报告口径说明里注明补报现象。
- 转发的融资新闻链接自带机构信息（投资方/轮次/FA），是机构表格的合法数据源，标＊。
- 群文件里 `poc-*.xlsx`、`*.py`、`semantic-completion.tar.gz` 是采集器/agent 测试文件，过滤；`纪要_*.pdf`、`*孵化*.pdf` 是业务文件，即使未下载成功也要列入报告附注。
